# /ml: sighting predictions

> **Everything here runs on SYNTHETIC data** generated by `synthetic.py` (made-up animals following
> hour-of-day patterns we chose). No real sighting has been used. Never present these numbers or
> predictions as real.

## What it does

For each (species, camera, hour) it predicts the probability of at least one sighting in that hour,
then turns the next 24 hours into `Prediction` rows ("Predicting an elk around 6:30 AM near Electric Peak Cam").

| file | job |
|---|---|
| `synthetic.py` | Deterministic synthetic sighting generator. Its `PROFILES` are the known truth: hour-of-day peaks, camera preference, weekend effect, noise. |
| `models.py` | Features, the three models, temporal split, metrics. |
| `evaluate.py` | Compares the models and prints the table below. |
| `predict.py` | Trains the hourly-profile model, writes `ml/out/predictions.json` (gitignored) and `web/public/predictions.sample.json`. |
| `katmai_analysis.py` | Combines local camera effort and detections with the public NPS Katmai species inventory; writes an honest descriptive JSON and Markdown report. |
| `fetch_gbif.py` | Downloads public brown-bear occurrence records from the official GBIF API for a documented Katmai regional envelope. |
| `make_seed.py` | Writes `supabase/seed.sql` from the same generator. |

## Run

Katmai three-camera setup and Windows commands: [KATMAI.md](KATMAI.md).
Use `python predict.py --park katmai --local-only --no-sample` for local synthetic
brown-bear predictions without database access or frontend sample changes.
`python evaluate.py --park katmai` evaluates the separate synthetic Katmai profile.
The results table below is for Yellowstone and does not measure Katmai performance.

```bash
cd ml
python -m venv .venv && source .venv/bin/activate   # Python 3.10+
pip install -r requirements.txt
python -m pytest                 # 10 tests
python evaluate.py               # the table below
python predict.py                # from /ml, or `python ml/predict.py` from the repo root; needs no keys
python make_seed.py              # regenerate supabase/seed.sql
python fetch_gbif.py             # cache public Katmai-region brown-bear records locally
python katmai_analysis.py        # local Katmai effort/detection and NPS inventory report
```

`katmai_analysis.py` reports detection frames per 100 captured frames with 95%
Wilson intervals, collection coverage, broad bear/bird rates, and the number of
approved present species in the NPS inventory. If `fetch_gbif.py` has run, it
also reports the monthly distribution of public brown-bear occurrence records.
Its output goes to
`ml/out/katmai_analysis.{json,md}`. These are survey summaries, not animal
population estimates. A short, single-day capture cannot support a seasonal or
hour-of-day forecast. GBIF records are opportunistic and cover a rectangular
regional envelope rather than the legal park boundary, so their monthly pattern
also reflects access, observer effort, reporting, and publication bias.

`predict.py` writes to Supabase only if `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are in the environment
(it also needs the `supabase` package from `worker/requirements.txt`). That path has never been run against a real project.

## Models

- **naive rate**: overall hourly hit rate per (species, camera); ignores the hour.
- **hourly profile**: hit rate per (species, camera, hour), lightly smoothed across neighbouring hours and shrunk toward the naive rate. Ignores weekday.
- **gradient boosting**: scikit-learn `HistGradientBoostingClassifier` on hour (sin/cos), weekday, sightings in the previous 7 days, species, camera.

## Results (synthetic, 42 days, train on the earlier days, test on the last 3 days, mean +/- sd over 5 generator seeds)

| model | Brier (lower better) | log loss (lower better) | hit rate +/-1 h | profile error vs truth (TV distance) |
|---|---|---|---|---|
| naive rate | 0.0227 +/- 0.0025 | 0.0989 +/- 0.0103 | 0.00 +/- 0.00 | 0.570 +/- 0.000 |
| hourly profile | 0.0212 +/- 0.0023 | 0.0838 +/- 0.0080 | 0.67 +/- 0.09 | 0.148 +/- 0.015 |
| gradient boosting | 0.0214 +/- 0.0024 | 0.0848 +/- 0.0086 | 0.61 +/- 0.11 | 0.201 +/- 0.035 |

- **Temporal split:** a test asserts the last training day is before the first test day; nothing is shuffled across time.
- **Hit rate:** for each (species, camera) pair with a real sighting in the test window, does the model's top hour fall within +/-1 h of a real sighting hour? The naive model has no hour preference (it ties, so the earliest hour wins), hence 0.
- **Recovery check:** because we know the true hourly curve for each species, "profile error" is the mean total-variation distance between each model's learned hour-of-day shape and the truth (0 = identical, 1 = disjoint). The naive model's flat shape scores 0.57.

### What this does and does not show

- Both learned models clearly beat the naive baseline, and the hourly profile recovers the true curves (error 0.15).
- **Gradient boosting did not beat the simpler hourly profile** (same Brier within noise, worse hit rate and profile error), so `predict.py` uses the hourly profile.
- The positive rate is only ~2% of hours and the test window is 3 days, so the differences between the two learned models are inside the seed-to-seed spread. Do not read more into them than that.
- **These results are optimistic.** The data follows smooth Gaussian bumps by construction, so a model that fits hour-of-day bumps looks good. Real sightings add weather, season, animal movement, camera downtime, detector misses (at dawn the Electric Peak cam is dark infrared and animals are small) and misclassifications. Real data would likely favour the boosting model only once there are months of history and extra features (temperature, daylight, day of year).

## Output format

`predictions.json` / `predictions.sample.json`:

```json
{"synthetic": true, "note": "...", "generated_at": "<UTC ISO>", "predictions": [...]}
```

`predictions.json` rows: `species`, `scientific_name`, `camera`, `predicted_for` (UTC start of the hour slot), `probability`.
The sample file's rows are shaped like a joined `predictions` row for the web card, with `offset_minutes` from `generated_at`
(add it to "now" to show the time relative to the visit): `id`, `offset_minutes`, `probability`,
`species {common_name, scientific_name}`, `camera {name, location}`. It is capped at one row per species, 6 rows, threshold 0.05.
